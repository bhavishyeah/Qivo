# Prioritized bug-fix pass: schedule datetime round-trip, auth token delivery, scheduled close sweep, template type safety

Eight audit findings fixed across the API and web packages. The web side corrects a datetime format mismatch that broke scheduled publish/close and brings the form-preview number handling in line with the live public form. The API side makes the session cookie name and session lifetime read from a single env source, removes dead cookie-writing code now that auth runs purely on a Bearer token in the response body, adds a scheduled-close sweep to complement the existing publish sweep, and tightens template typing so the `/from-template` path no longer needs an `as any` escape hatch. Changes are localized to the files named in the task plan; no unrelated refactors. Both typechecks exit 0.

Watch for: nothing blocking. One behavioral note (confirmed) — `toDatetimeLocal`/`toIsoInstant` round-trip through the viewer's local timezone, so a form edited in one timezone and reopened in another shows the equivalent local wall-clock time, not the original author's; this is correct for datetime-local inputs and matches the backend's instant storage.

**Verdict**: APPROVED

## High-level view

The schedule fix (CRITICAL-1) is a pure client-side boundary conversion. The datetime-local input produces local wall-clock text with no zone; the old code shipped that raw string to a backend field validated as `z.string().datetime()`, which rejected it. The fix converts to a full ISO instant on save and back to local wall-clock on load, with invalid/empty input collapsing to null/empty. The backend Zod schema is deliberately untouched.

The preview number parity fix (HIGH-1) replaces a one-liner that coerced every number input through `Number(...)` — turning a cleared field into `0` and bad input into `NaN` — with the exact logic the public form uses: empty stays unanswered, non-numeric collapses to empty, valid becomes a number. The two handlers are now identical.

On auth, the cookie name and session length are now sourced from `env` in every reader (HIGH-3, MEDIUM-2), and the cookie-writing paths were removed entirely (HIGH-2) because the system already authenticates off a Bearer token returned in the JSON body and read from localStorage on the client. Login/signup/google still return that token; logout still deletes the DB session. The cookie-read fallback in the auth middleware is retained via the env name, so any legacy cookie still works.

The scheduled-close sweep (MEDIUM-1) mirrors the existing publish sweep: a new `closeDueForms` flips `PUBLISHED` forms past their `scheduledCloseAt` to `CLOSED`, wired into the same 60s timer tick, with the per-request close check kept as a safety net.

The template typing cleanup (MEDIUM-3, MEDIUM-4) exports the `QuestionType` union, types `TemplateQuestion.type` against it, and fixes the event-registration phone field to `PHONE` — which is what let the `as any` in the `/from-template` handler be removed without a type error.

### Schedule datetime round-trip (CRITICAL-1)

Two module-scope helpers in `FormEditorPage.tsx` form the client-side boundary. `toIsoInstant` takes the datetime-local string, builds a `Date`, and returns `d.toISOString()` (a `…Z` instant the backend's `z.string().datetime()` accepts) or `null` for empty/invalid input. `toDatetimeLocal` reverses it: it shifts a stored ISO instant by the local timezone offset and slices to `YYYY-MM-DDTHH:mm` so the datetime-local input renders the viewer's local wall-clock. Both guard with `Number.isNaN(d.getTime())`, so a malformed stored value yields `""` on load and a malformed input yields `null` on save rather than throwing or sending `Invalid Date`.

The wiring: load replaces the raw `?? ""` reads with `toDatetimeLocal(...)`, save replaces the `|| null` passthrough with `toIsoInstant(...)`. The datetime-local inputs and the backend `updateFormSettingsSchema` are untouched, so the fix lives entirely at the client boundary as required. The timezone-translation behavior noted in the summary (the stored value is an instant, rendered in the viewer's local zone) is the correct semantics for a datetime-local control bound to an instant field — worth knowing, not a defect.

### Preview number parity with the public form (HIGH-1)

`FormPreviewPage.handleInputChange` now carries the same three-way number handling as `PublicFormPage`: empty string stays `""` (unanswered), a non-numeric value collapses to `""` instead of `NaN`, and a valid value is stored as a parsed number; non-number inputs pass through raw. I diffed the two handler bodies and they are identical, including the explanatory comment. This closes the gap where a cleared required number field in preview could silently submit `0` and pass validation.

### Auth cookie name and session length from env (HIGH-3, MEDIUM-2)

`middleware/auth.ts` now imports `env` and reads `req.cookies?.[env.SESSION_COOKIE_NAME]`, keeping the Bearer `Authorization` header as the primary path with the cookie as fallback. A repo-wide search confirms the only remaining `qivo_session` literal is the default in `config/env.ts` — no hardcoded literal survives in the auth code paths.

Session lifetime is unified the same way: both `auth.service.ts` and `google.service.ts` drop their local `const SESSION_DAYS = 30` and compute `createSessionExpiry()` from `env.SESSION_DAYS`.

### Removing dead cookie-writing code (HIGH-2)

```
client (localStorage Bearer)  ──Authorization: Bearer <token>──▶  requireAuth
   ▲                                                                  │
   └── token: result.sessionToken (JSON body) ◀── login/signup/google ┘
```

The three `res.cookie(...)` calls (signup/login/google) and the logout `res.clearCookie(...)` were removed, along with the now-unused `cookie.js` import. This is safe because the cookie was never the sole token channel: I confirmed all three handlers still return `token: result.sessionToken` in `data.token`, and logout still calls `logout(req.sessionId)`, which deletes the DB session. The client reads the Bearer token from localStorage and never sends `credentials: 'include'`, so dropping the Set-Cookie has no effect on the live auth flow. The middleware's cookie-read fallback was intentionally kept (now via `env.SESSION_COOKIE_NAME`), so any pre-existing cookie still resolves. `config/cookie.ts` was left in place and CSRF/origin/cookie-parser middleware were not touched.

One deliberate deviation from the literal plan, which called for adding an `env` import to `auth.routes.ts`: after HIGH-2 removed every cookie call there, `auth.routes.ts` has no remaining `env` usage, and the strict tsconfig (with `verbatimModuleSyntax`) would fail on an unused import. A reference comment was added instead of a dead import. This is the correct call — it satisfies the intent (single source of truth, no hardcoded literal) without breaking the typecheck.

### Scheduled-close sweep (MEDIUM-1)

`closeDueForms(now = new Date())` mirrors `publishDueForms`: it selects `{ deletedAt: null, status: "PUBLISHED" }` forms with their `schema`, filters to those whose `getFormSchema(f.schema).settings.scheduledCloseAt` parses to a valid `Date <= now`, and issues a single `updateMany` to `status: "CLOSED"`, returning the count (0 when nothing is due). The `CLOSED` literal matches the Prisma `FormStatus` enum. It is wired into `server.ts` by extending `runPublishSweep` to call it in the same 60s tick and log the closed count when positive; the catch-log was broadened to "publish/close sweep failed". The per-request close check in `submitFormResponse` remains as a safety net, so a form still closes on first access even if a sweep is missed.

### Template type safety (MEDIUM-3, MEDIUM-4)

The `QuestionType` union in `form.service.ts` is now exported. `templates.ts` imports it as a type and declares `TemplateQuestion.type: QuestionType` instead of `string`, and the event-registration "Phone Number" field is corrected from `SHORT_TEXT` to `PHONE` (a valid union member). With the template entries now provably typed against the union, the `/from-template` handler in `form.routes.ts` drops `type: q.type as any` for `type: q.type`, and a repo search confirms no `as any` remains in that file — the cast is gone because the types line up, not suppressed.
