# Design: Answer Piping (labels only)

## Overview

Answer piping lets a question **label** reference an earlier question's current answer through a `{{...}}` token. As the respondent fills the form, any later label that pipes an earlier answer updates live. Example: question A asks "Team captain name?" and a later question's label is set to `Confirm {{question_A}}'s jersey size` — once the respondent types "Priya" into A, the later label renders `Confirm Priya's jersey size`.

Scope for this version is **labels only**. Descriptions and the confirmation message are explicitly out of scope. Piping is a pure **display-time** transformation: nothing about how answers are stored or validated changes, and the backend is unaffected (confirmed in the Backend section below).

The implementation is deliberately small and mirrors the existing `evaluateConditions` precedent. It adds one new library file (`apps/web/src/lib/piping.ts`) with a resolver function, wires that resolver into the two respondent-facing renderers (`PublicFormPage.tsx` and `FormPreviewPage.tsx`) at the point where `question.label` is rendered, and adds a small "insert reference" affordance plus a raw-token-aware label preview to the builder (`FormEditorPage.tsx`). The technology stack is **locked**: TypeScript + React (Vite) on the web side, reusing the existing `AnswerValue` / `Question` / `QuestionOption` types from `apps/web/src/types/index.ts`. No new dependencies.

## Token syntax and regex (decision 1)

**Token syntax:** `{{<questionId>}}` — two opening braces, the stable question id, two closing braces, with optional surrounding whitespace tolerated inside the braces (`{{ question_abc123 }}`). Question ids in this codebase are generated by `createQuestionId()` on the API and are of the form `question_<alnum>` (see `form.service.ts`), i.e. they match `[A-Za-z0-9_]+`.

**Regex (pinned):**

```ts
// Matches {{ questionId }} capturing the trimmed id. Global so we can replace all.
const PIPING_TOKEN_RE = /\{\{\s*([A-Za-z0-9_]+)\s*\}\}/g;
```

Rationale and robustness:

- The character class `[A-Za-z0-9_]+` only matches well-formed ids, so malformed tokens never produce a capture group that could be mis-resolved.
- A stray `{` or `{{` with no closing pair, or `{{}}` (empty), or `{{ foo-bar }}` (hyphen not in class) simply **does not match** and is left in the label verbatim. This is the "don't choke on malformed tokens" requirement: non-matches are passed through untouched rather than throwing or eating characters.
- Nested braces such as `{{{{x}}}}` are handled by the regex engine matching the innermost valid `{{x}}` once; any surplus literal braces remain as text. No recursion, no catastrophic backtracking (the pattern is linear).
- **Unknown id** (a token whose id is not found in the form's question set): resolves to **empty string** (the token is removed). This is the benign, non-confusing choice — a dangling reference to a deleted question should not leak `{{question_deleted}}` to a respondent. This is distinct from the *fallback rule* below, which is about a known-but-unanswered question.

## Resolver signature and behavior

New file: **`apps/web/src/lib/piping.ts`**.

```ts
import type { AnswerValue, Question } from "../types";

/**
 * Resolve piping tokens in a label string against the live answers map.
 * Mirrors conditions.ts value-handling (string as-is, string[] joined, empty-aware).
 *
 * @param label      the raw label, possibly containing {{questionId}} tokens
 * @param questions  all questions in the form (flattened), used to look up the
 *                   referenced question's type/required/options
 * @param answers    the live answers map (same shape conditions.ts reads)
 */
export function resolvePipedLabel(
  label: string,
  questions: Question[],
  answers: Record<string, AnswerValue>,
): string;
```

Why `questions: Question[]` rather than a map: both renderers already have a flattened list of questions in scope (`allQuestions` in `PublicFormPage`, and the per-section `questions` plus `form.schema.sections` in `FormPreviewPage`). Passing the flat list lets the resolver look up the referenced question by id to read its `required` flag (for the fallback rule) and its `options` (for value→label resolution). The resolver builds its own `Map<string, Question>` internally once per call.

Internal helper that converts a single referenced question's answer to display text (reuses conditions.ts style):

```ts
function renderAnswerValue(question: Question, value: AnswerValue): string {
  // string[] (MULTIPLE_CHOICE / MULTI_ENTRY) -> join non-empty entries with ", "
  // plain string -> as-is
  // number -> String(number)
  // choice types -> prefer option.label over raw value (see decision 3)
}
```

Replacement loop: `label.replace(PIPING_TOKEN_RE, (_, id) => resolveToken(id))`. `resolveToken(id)`:

1. Look up `q = byId.get(id)`. If missing → return `""` (unknown id, per decision 1).
2. Read `value = answers[id]`.
3. Determine "answered": `value` is considered unanswered when it is `undefined`, `null`, `""`, an empty array, or an array whose entries are all blank after `.trim()` — **exactly** the emptiness test used by `validateSection`/`validateAll` in `PublicFormPage` and `submitFormResponse` on the API, so "answered for piping" and "answered for validation" never disagree.
4. If unanswered → apply the **fallback rule** (decision 2): `q.required` → return the fallback error string; otherwise return `""` (blank).
5. If answered → return `renderAnswerValue(q, value)`.

## Value rendering and choice value→label (decision 3)

Reuse the `conditions.ts` handling style:

- **Plain string** (`SHORT_TEXT`, `LONG_TEXT`, `EMAIL`, `PHONE`, `URL`, `DATE`, `YES_NO`, `SINGLE_CHOICE` raw value): render as-is.
- **number** (`NUMBER`, `RATING`, `LINEAR_SCALE`): `String(value)`.
- **string[]** (`MULTIPLE_CHOICE`, `MULTI_ENTRY`): join with `", "`, skipping blank/whitespace-only entries so a half-filled MULTI_ENTRY doesn't render `", , "`.

**Choice value→label: DO IT for v1.** The referenced question's `options` are available to the resolver (we pass the full `Question`), so resolving a stored option `value` to its human `label` is cheap and strictly better UX — a piped `SINGLE_CHOICE` should show "Red", not "option_1". Rules:

- `SINGLE_CHOICE`: find `options.find(o => o.value === value)`; render `option.label` if found, else the raw string value (defensive — a stored value with no matching option, e.g. after the option was deleted).
- `MULTIPLE_CHOICE`: map each selected value through the same lookup, falling back to the raw value per entry, then join with `", "`.
- `YES_NO`: stored as `"yes"`/`"no"`; render `"Yes"`/`"No"` (mirrors the `[{value:"yes",label:"Yes"},{value:"no",label:"No"}]` the renderers already synthesize). Implement as a tiny built-in map since `YES_NO` carries no `options`.

For every other type there is no value→label concept, so the raw string/number is used.

## Fallback error copy (decision 2)

When the referenced question is **required** and **not yet answered**, the token is replaced by this exact inline string:

```
[answer "<referenced question label>" first]
```

The `<referenced question label>` is the referenced question's own `label`. If that label itself contains piping tokens, it is **not** recursively resolved — we insert the raw label text (trimmed) to avoid recursion and keep behavior bounded; in the common case an earlier label has no tokens anyway. Example rendered output: `Confirm [answer "Team captain name" first]'s jersey size`.

When the referenced question is **not required** and unanswered, the token resolves to `""` (empty string / blank), per the user spec.

This fallback string is produced by the resolver and carries no markup. The renderers already render the whole resolved label as plain text inside the existing `<span class="question-label">`, so the fallback shows inline exactly where the token sat. No new validation is introduced — this is display-only guidance, and the real required-answer enforcement is the pre-existing `validateSection`/`validateAll`/server check on the piping question itself (not the referenced one).

## Web integration points

### PublicFormPage.tsx (respondent renderer)

`allQuestions` is already computed (`sections.flatMap((s) => s.questions)`) and `answers` state already drives re-render on every keystroke via `updateAnswer`/`handleInputChange`. The `QuestionField` component renders `question.label` in its `label` JSX:

```tsx
const label = (
  <span className="question-label">
    {question.label}
    {question.required ? <span className="required-mark"> *</span> : null}
  </span>
);
```

Change: pass `allQuestions` and `answers` down to `QuestionField` (two new props), and resolve the label once:

```tsx
const resolvedLabel = resolvePipedLabel(question.label, allQuestions, answers);
// ...
<span className="question-label">
  {resolvedLabel}
  {question.required ? <span className="required-mark"> *</span> : null}
</span>
```

Because `QuestionField` is re-rendered with fresh `answers` whenever any answer changes (it's already keyed and receives `value={answers[question.id]}` and the parent re-renders on `setAnswers`), **no extra wiring is needed for live updates** (decision/spec item 5 confirmed). The `aria-label={question.label}` usages inside rating/scale fieldsets should also use `resolvedLabel` so assistive tech reads the resolved text.

### FormPreviewPage.tsx (preview renderer — parity)

Identical treatment. The preview has `form.schema.sections`; compute a flattened `allQuestions` with `useMemo(() => sections.flatMap(s => s.questions), [sections])` (the page currently only flattens the *current* section's visible questions, so this is a small addition), pass `allQuestions` + `answers` into `PreviewQuestion`, and resolve `question.label` the same way. This keeps preview output byte-for-byte consistent with the public form, including the fallback copy and choice label resolution.

### FormEditorPage.tsx (builder)

Two additions, both inside the active `QuestionCard` (which already receives `allQuestions` and its global `index`, and already renders a `ConditionEditor` using the earlier-questions-only filter).

**(a) Insert-reference affordance (decision 4).** Directly beneath the "Question label" input, add an "Insert answer reference ▾" control. Reuse the *exact* earlier-questions filter from `ConditionEditor`:

```ts
const availableQuestions = allQuestions.filter(
  (q) => q.id !== question.id && allQuestions.indexOf(q) < allQuestions.indexOf(question),
);
```

Render it as a small `<select>` (simplest, matches the existing condition dropdown styling) with a disabled placeholder option "Insert answer reference", followed by one `<option>` per earlier question showing `q.label.slice(0, 30)`. On change, **append** `{{<id>}}` to the current label (append is the pinned mechanism — simplest and acceptable per decision 4):

```ts
function insertReference(id: string) {
  const sep = question.label && !question.label.endsWith(" ") ? " " : "";
  onChange(question.id, { label: `${question.label}${sep}{{${id}}}` });
}
```

The control is **disabled when `availableQuestions.length === 0`** (the first question has nothing to pipe), with `title="Add questions above first"` — mirroring how `ConditionEditor` disables "+ Add condition". After selection the `<select>` resets to its placeholder so the same reference can be inserted again.

**(b) Editor label preview (decision 5).** Keep it simple: in the editor the label `<input>` continues to show the **raw** token text (`{{question_abc123}}`) — this is what the author is editing, and showing it raw is unambiguous and avoids a two-way transform in the input. Below the label input, when the raw label contains at least one token, render a single muted helper line that shows the **resolved-with-placeholders** preview using the referenced questions' labels, e.g.:

```
Preview: Confirm [Team captain name]'s jersey size
```

This is produced by a tiny editor-only helper (not the runtime resolver) that replaces each `{{id}}` with `[<referenced question label>]` (or `[unknown reference]` if the id isn't found). It gives the author a human-readable sense of the token without needing live answers, and never appears to respondents. The **inactive** QuestionCard view (`question.label || "Untitled question"`) can keep showing raw tokens — it's a compact listing and low-stakes; no change needed there.

## Backend (decision 6): NO change required

Confirmed by reading `apps/api/src/modules/forms/form.service.ts`:

- Labels are stored verbatim (`question.label = input.label.trim()`), so a label containing `{{...}}` is persisted and served unchanged. That is exactly what the web resolver expects.
- `validateAnswerAgainstQuestion` and the required-check in `submitFormResponse` key off `question.id` and the submitted `answers[id]` values — never off label text. Piping does not alter stored answers or their validation.
- Visibility (`isQuestionVisible`) is condition-based, independent of labels.

**One noted edge (not fixed in v1, intentionally out of scope):** two server-side places render `question.label` as text — the respondent confirmation email (`buildAnswerSummary`) and the analytics `QuestionReport.label`. These would show the **raw** `{{...}}` token rather than a resolved value. This is acceptable for v1 because (a) the feature scope is explicitly the live form label only, and (b) resolving on the server would require per-response answer substitution with the same fallback semantics, which is additional scope the user did not request. Flagged here so a future iteration can decide whether the confirmation email should resolve piping. **No backend code changes are made in this task.**

## Edge cases

- **Referenced question answered after the piping question is shown:** conditional logic + section ordering normally guarantee the earlier question is answered first, but the resolver handles the not-yet-answered case directly via the fallback rule, so ordering is not relied upon.
- **Referenced question hidden by conditions:** its answer is simply absent/empty in `answers`, so it resolves via the unanswered path (blank or fallback). No special handling.
- **Deleted referenced question (dangling id):** unknown id → blank (decision 1).
- **Token referencing the question's own id or a later question:** the runtime resolver still resolves it if an answer exists, but the editor only ever *inserts* earlier-question tokens (the `availableQuestions` filter), so authors cannot create forward/self references through the UI. A hand-crafted forward reference degrades gracefully to blank/fallback.
- **Label that is only a token** (`{{question_x}}`): resolves to the answer, the fallback string, or blank — a fully blank label is allowed (the respondent just sees the input with no visible label text, same as today for an empty label).
- **Malformed/partial braces:** passed through verbatim (regex non-match).
- **Choice option deleted after being selected:** value→label lookup misses → raw stored value is rendered (defensive fallback).

## Testability

- **Unit (pure, no React):** `resolvePipedLabel` in `piping.ts` is a pure function and gets the bulk of the coverage — single token, multiple tokens in one label, unknown id → blank, malformed token passthrough, required-unanswered → exact fallback copy, not-required-unanswered → blank, string / number / `string[]` / MULTI_ENTRY join, `SINGLE_CHOICE` and `MULTIPLE_CHOICE` value→label, `YES_NO` mapping, option-deleted fallback. These are the highest-value tests and require no DOM.
- **Component / integration:** render `PublicFormPage` (or the `QuestionField`) with a seeded form where a later label pipes an earlier one; assert the label text updates after simulating input into the earlier field (covers the live-update render path and prop wiring). Preview parity can be asserted the same way against `FormPreviewPage`.
- **Editor:** assert the insert `<select>` lists only earlier questions and that selecting one appends `{{id}}` to the label; assert the helper preview line shows `[referenced label]`.
- The design is test-friendly precisely because the logic lives in one pure resolver and the renderers only do substitution-at-render, with no new state or effects to mock.
